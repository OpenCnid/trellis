Read the diagram three ways

Connection

Two wires, one device

The only links between guest and host are two AF_VSOCK ports on one virtio-vsock device: llm_query (the RLM recursion, carrying the identical 4-byte-length + JSON frame) and the DB RPC (run_query / run_cypher). Nothing else connects the two zones.

Overlap

A deliberately thin seam

Where the trust zones touch is narrow by design: a set of CapabilityDescriptor stubs and a length-prefixed frame. No live objects, no raw sockets, and no credentials cross — only serialized calls out and results back. That thin overlap is what lets the backend be swapped without touching a caller.

Isolation

Three nested facts

The worker sits inside a KVM hardware boundary (optionally + gVisor); the Postgres and Neo4j credentials exist only in the host broker; and every route out except vsock is denied by default at the NIC — a guest-side denylist would not count, because attacker-root could flush it.

Why not CubeSandbox — yet

Verdict: NOT-YETre-evaluate after two gates close
  • CubeEgress is L7 HTTP/HTTPS-only. It cannot frame or gate Postgres wire or Neo4j Bolt (raw binary TCP), so it offers zero off-the-shelf value for Trellis' actual tool traffic — the DB broker is built either way, and vsock is the cleaner substrate.
  • An open sandbox-escape-class issue (#838) sits against the exact trust-boundary code, alongside no security policy, no third-party audit, a ~3-month history, and an unstable release cadence.
  • Workload-shape mismatch. CubeSandbox optimizes for many short-lived ephemeral executions; Trellis needs one persistent, stateful worker per session — Kata's model.

Depth 1 — flat parallel sub-LLM fan-out (hardened)

This is the live design (max_depth 1): the root worker splits context and issues N parallel flat sub-LLM calls — no child REPLs, no child sandboxes, no recursion (max_depth 2 was measured to degrade quality). Every crossing is a guarded host-side chokepoint, and the one truth to sit with: deny-by-default egress blocks the NIC but does not stop exfiltration — the sanctioned crossings carry model-controlled text out, so the real guards are content-DLP, CID-keyed caps, and a read-only broker. The design must hold even under fully successful prompt injection.

The judged selection

Four-role panel · promote-weakened

Among the finalists Kata / gVisor / Firecracker, the panel endorses Kata (on Cloud Hypervisor) as the primary boundary for Trellis' profile — gVisor optional/deferred, Firecracker as the VMM beneath Kata.

medium-high confidence · the panel refined rather than overturned the recommendation, and independently flagged the gVisor-nesting as the weakest link

Category

Not a flat three-way

Firecracker is a VMM; Kata runs on a VMM; gVisor is a different layer. The real axes: microVM vs gVisor, then Kata vs bare Firecracker.

Threat tier

microVM is context-dependent

Operators are split — Modal runs gVisor-alone at 50k+ concurrency. A microVM is the right primary for Trellis' adversarial, model-authored code specifically.

Integrity

The catch, kept

The audit flagged the "build-lift" argument as the author's own convenience — and the one item no judge scrutinized. Build-lift is not a security argument.
