Why a trellis

Chain of density (Adams et al. 2023, arXiv:2309.04269) rewrites one summary five times at a fixed length, fusing new entities in by compressing what is already there. Fixed length is the engine: drop it and “add detail” produces a longer summary, never a denser one.

A density-trellis is the second tier of that format — several density-chains stacked together. One shared trunk, one five-tier chain per subsystem class, and a lattice of cross-links so the branches interlock instead of standing in parallel columns. A single spine carries one salience order; a system has many at once. Each branch's tiers traverse time on their own: T1 essence → T2–T3 shipped machinery with receipts → T4 the frontier → T5 future plans.

The trunk

T0 — ONE SENTENCE

Trellis is a personalized composable expert system whose expertise is the user's data — built as OpenCnid's Recursive Language Model runtime, where the user's context, memory, knowledge and capabilities live as queryable engine state with enforced provenance, the model reaches all of it only by writing code, and because the expertise is the user's data the user is the domain authority.

T1 — ONE PARAGRAPH

The substrate turns every source into an immutable SHA-256 Merkle AST in PostgreSQL (Tier 1) and every derived belief into a Neo4j node carrying sourceNodeIds — the exact block hashes it came from (Tier 2); a Tier-3 workspace has no trust standing. The execution model is the RLM: context is a database, not a scroll, reached by writing Python and calling llm_query over slices. Trust moves one way, upward, only through operator-gated promotion. Two flywheels compound — derived facts cached once and reused, and the system's own instructions versioned as modules governed as beliefs. One discipline binds text handling — code-mediated text: the model never counts, never copies. Orthogonal to custody, a signed-ternary standing model (−1 doubt · 0 belief · +1 fact) grades how a claim held up, moved only by evidence or a user gate. And every evaluating function composes per context from primitives; there is no default cast.

T2 — THE CLASS MAP

Seeds: C1 REPL & RLM · C2 Engineering loop · C3 Epistemic support. Branch-out: C4 Substrate & custody · C5 Code-mediated text · C6 Trust & flywheels · C7 Standing & composition. Frontier: C8 Backend seam & TTT · C9 Mechinterp sidecar · C10 Benchmarks · C11 Serving & governance · C12 REPL sandbox · C13 Self-describing surfaces.

The weave: C1 runs on C4/C5; C6 rises out of C4 and is the only bridge up into it; C3 grades C4's beliefs and feeds C7's standing axis; C7's composition law governs C3 and the skills; C2 mechanizes the loop that produces all of it; C8/C9 are the research inflow; C12 is the trust boundary C1 does not yet have; C10 is the evidence gate on every claim; C11 is the skin; C13 is how the whole thing explains itself — including this file.

Maintenance — the living-wiki loop

The map is maintained by machine-detected staleness, not by memory. npm run wiki:check diffs the working tree against the pinned snapshot_commit, routes every changed path through class-map.json, and names which branch classes went stale. A Stop hook runs the same checker and raises the roster once per session.

  • One updating sub-agent per touched class. Siblings cannot see each other, so a per-class agent cannot smear one subsystem's status onto another's; the cross-cutting composition belongs to whoever assembles their returns.
  • Densify, never append. New machinery enters T4 first and rises toward T1 only as the concept changes. At a fixed budget, adding means evicting — visible in the diff.
  • Hold the layer test. Each tier, read alone, must still be true.
